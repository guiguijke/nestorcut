# Audit de bout en bout — priorités 3 (éclatement / échelle) et 4 (`.job` SheetCam)

Consigne du vérificateur à l'implémenteur, 14/09, à la demande du
propriétaire : « faire un tour d'audit sur les deux dernières features et
vérifier de bout en bout que c'est OK ». L'implémenteur exécute cet audit à
la place du vérificateur ; le vérificateur rejoue ensuite un échantillon et
rend le verdict. Le gel des nouveautés reste en vigueur : tout constat rouge
devient un lot correctif court.

## 0. Règles de l'audit

- **Images à HEAD** (`app`, `user-file-processing-worker`, `nesting-worker`)
  reconstruites depuis les sources avant tout banc ; le SHA de la page
  locale égale HEAD.
- **Mesurer, jamais supposer** : chaque ligne du rapport porte ce qui a été
  fait, ce qui a été lu (à l'écran, dans IndexedDB, dans Mongo, dans le
  fichier rendu) et le chiffre. Un scénario non joué est écrit « non joué »,
  pas omis.
- **Fichiers réels sous identifiants neutres** dans le rapport ; les copies
  vont dans `~/qa-out/audit-e2e/`, jamais dans `docs/`. Aucune écriture en
  production : tout se joue sur la pile locale (les deux modes, « Cet
  appareil » et « Nos serveurs », le second avec le compte de test granté).
- Chaque scénario se termine par le **fichier rendu relu par un outil
  indépendant** : DXF relu par notre importeur (compte de pièces, positions
  relatives) ; `.job` relu par `parseSheetCamJob` (sections, `Count`,
  `[OpOrder]`, binaire, points de départ) — et, pour les `.job`, un fichier
  par famille remis au propriétaire pour SheetCam.
- Le rapport suit l'ordre des tableaux ci-dessous, constat par constat, avec
  la colonne « cause probable » remplie pour chaque rouge et une proposition
  de lot correctif (périmètre, verrou, durée).

## 1. Priorité 3 — dessin multi-pièces, échelle, éclatement

Fichiers : le dessin du collègue (17 pièces, splines) ; **trois autres
fichiers multi-pièces du corpus** (`specs/import-corpus/`, identifiants par
préfixe de hash) choisis pour couvrir : un dessin avec contours imbriqués
(pièce dans pièce), un dessin dense (pièces proches à moins de 4 mm), un
dessin à plus de 50 pièces ; plus `Piece_Trou.DXF` comme témoin à une pièce.

| # | Scénario | À mesurer |
|---|---|---|
| P3-1 | Dépôt tel quel, mode local | une fiche « 1 bloc · N pièces · L × H », N et L × H égaux à ceux de l'import (compter les pièces par notre importeur) ; aucune lecture wasm de plus que import + canonique |

| P3-3 | Bloc en **quantité 3** sur une tôle qui admet 2 blocs | 2 blocs sur la tôle 1, 1 sur la tôle 2 ; rapport « 3 blocs (3N pièces) » ; aucun chevauchement entre blocs (mesure arête à arête sur les enveloppes ≥ espacement) |

## 2. Priorité 4 — `.job` SheetCam (mode local)

Fichiers : la série `.testparts/retro-eng-job/` (pièce L, 17 fichiers),
`Piece_Trou+Fill_x4_OK.job` et ses variantes, et **au moins un `.job` réel
d'atelier** fourni par le propriétaire (plus de 7 dessins, noms accentués,
plusieurs opérations).

| # | Scénario | À mesurer |
|---|---|---|
| P4-1 | Dépôt `.job` + DXF, tous les fichiers de la série | fiches = dessins distincts, quantités = exemplaires (`copyOf` comptés), tôle et kerf pré-remplis, espacement affiché = 2 × kerf + 1 ; aucun « dessin manquant » à tort (noms accentués, casse) |
| P4-2 | `.job` déposé **sans** un de ses DXF | le dessin manquant est NOMMÉ ; les autres fiches créées ; nesting possible sur ce qui est là |
| P4-3 | Points de départ : automatique / déplacé à la main / 4 coins | constat par contour (utilisateur / NestorCut) ; point déplacé octet-identique ; point automatique figé avec drapeau ; `.job` rendu relu : valeurs attendues |
| P4-4 | Types d'amorce None / Arc / Tangent / Perpendicular, entrée 5 sortie 10 | réserve appliquée avec la bonne enveloppe (mesure des 36 points des `.nc` déjà en verrou) ; aucun trou retiré sans raison ; rayon de perçage 2 × kerf |
| P4-5 | Kerf 0 (0,0001) et kerf 4 | repli 3 mm dit pour kerf ~0 ; disque 8 mm pour kerf 4 ; espacement 1 et 9 mm affichés |
| P4-6 | Nesting avec nichage possible (espacement ramené à 2 mm par l'utilisateur) | nichées coupées avant l'hôte dans `[OpOrder]` ; réserve du trou respectée : distance amorce ↔ nichée ≥ espacement ; **fichier remis au propriétaire pour SheetCam** |
| P4-7 | Poses : rotations 90 / 180 / 270 et **45°** (rotationCount 8), miroir refusé ou géré | `XPos/YPos/Angle` par la formule J2 ; pour 45°, reconstruction des points de départ à ≤ 1 mm contre la géométrie (le fichier « + 45deg » sert de référence) ; angles dans (−2π, 0] |
| P4-8 | **Plusieurs tôles** (stock 2, pièces qui débordent) | un `.job` par tôle, `_tole1`, `_tole2` ; chaque fichier n'active que ses pièces ; `Count` cohérent ; binaire identique hors drapeaux |
| P4-9 | `.job` déjà nesté par NestorCut **redéposé** | pas de pièces fantômes ; copies réutilisées ; résultat cohérent |
| P4-10 | `.job` réel d'atelier (> 7 dessins, accents, opérations multiples) | appariement des blocs du binaire par la géométrie sur TOUS les dessins ; aucune fiche perdue ; `.job` rendu s'ouvre dans SheetCam (propriétaire) |
| P4-11 | Un DXF du `.job` qui n'importe pas (fichier corrompu) | refus nommé, les autres fiches vivent, le `.job` rendu n'écrit que les pièces présentes |
| P4-12 | Suppression d'une fiche `.job` puis nesting | le `.job` rendu désactive la pièce supprimée, `Count` juste |
| P4-13 | Projet **serveur** avec un `.job` | comportement DIT (J5 non livré) : le `.job` est-il refusé proprement, ignoré, ou traité ? Aucune erreur muette |
| P4-14 | Résultat : vue DXF, téléchargement `.job` ET DXF, CSV | réactif ; les deux fichiers cohérents entre eux (mêmes poses) |
